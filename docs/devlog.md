## 1단계: TCP로 처음 말 걸기 (2026-10-27)

### 🎯 목표
라즈베리파이(현장)가 측정값을 서버(본사)에 **TCP로 보내고**, 서버가 그 값을 **화면에 찍는** 것까지.

### 🛠️ 한 일
- **메시지 규칙(프로토콜) 만들기** (`common/protocol.py`)
  - 모든 메시지 앞에 **4바이트 길이**를 붙이고, 내용은 JSON으로.
  - 받는 쪽은 `recv_exact()`로 **정확히 그 길이만큼** 다 받을 때까지 반복해서 받음.
- **서버:** 메인 쓰레드는 전화(접속)만 받고, 접속마다 **전담 직원(ClientHandler 쓰레드)**을 한 명씩 붙임.
- **에이전트:** 측정 담당(SensorThread)이 2초마다 측정해서 **큐(대기 줄)**에 넣고, 보고 담당(SenderThread)이 꺼내서 보냄.
- **가짜 센서(Mock):** 부품 없이 PC에서 돌릴 수 있게 랜덤 값을 만드는 센서.
- 연결이 끊기면 3초 뒤 다시 연결.

### 💡 쉽게 이해하기
> TCP는 물을 흘려보내는 **파이프**다. "컵 두 잔"을 따로 부어도 받는 쪽엔 물줄기로 섞여서 온다.
> 그래서 "이번 건 87바이트"라는 **길이표**를 앞에 붙여야 받는 쪽이 정확히 잘라낼 수 있다.

> 측정과 전송을 **다른 직원**이 하게 한 이유: 전송이 막혀도(연결 끊김) 측정은 계속돼야 하니까.
> 두 직원 사이는 **큐**로 이어서, 측정 담당은 넣기만 하고 보고 담당은 꺼내기만 한다.

### 🧱 부딪힌 문제
| 문제 | 원인 | 해결 |
|---|---|---|
| `python` 명령이 안 됨 | Windows에서 `python`은 스토어 바로가기일 뿐 | `py` 런처로 실행 (`py -m server.main`) |
| 로그를 파일로 저장하면 한글·이모지가 깨짐 | Windows 기본 인코딩(cp949) | 로그 출력을 UTF-8로 고정 (`setup_logging`) |
| 보내는 순간 연결이 끊기면 그 보고가 사라짐 | 보내고 나면 바로 버리기 때문 | **5단계에서 해결 예정** (재전송 버퍼) |

## 2단계: 양방향 통신 + 판정 (2026-10-27)

### 🎯 목표
서버가 값을 보고 **"위험한가?"를 판정**해서, **같은 연결로** 현장에 "빨간불 켜!" 같은 **지시(CMD)**를 보내기.

### 🛠️ 한 일
- **AlarmEngine** (`server/alarm.py`): 온도·습도·누수·거리를 보고 NORMAL / WARN / DANGER / ACCESS 판정.
- **상태가 바뀔 때만** CMD를 보냄 (2초마다 "빨간불 켜"를 반복하지 않게).
- **에이전트에 듣기 담당(ReceiverThread)** 추가: 서버 지시를 받아 LED·부저를 움직임.
- **가짜 LED·부저(MockActuator):** 터미널에 💡, 🔊 로 표시.
- **KeyboardThread:** 키보드로 `t`(과열), `l`(누수) 등을 눌러 상황을 연출.
- **경보 해제 버튼:** 누르면 부저는 **현장에서 바로** 끄고, 서버에 EVENT로 알림.

### 💡 쉽게 이해하기
> 전화 한 통으로 **말하기와 듣기를 동시에** 한다. 그래서 에이전트에는 "말하는 직원"과 "듣는 직원"이 따로 있다.
> 듣는 직원은 서버가 언제 말할지 모르니 계속 귀를 대고 기다린다.

> 버튼을 누를 때(키보드 쓰레드)와 보고할 때(SenderThread)가 **같은 전화기에 동시에** 말하면 말이 섞인다.
> 그래서 전화기에 **열쇠(`send_lock`)**를 달아 한 번에 한 명만 말하게 했다.

### 🧱 부딪힌 문제
| 문제 | 원인 | 해결 |
|---|---|---|
| 메시지를 받는 **도중에** 타임아웃이 나면 나머지 바이트가 다음 메시지로 착각될 위험 | 타임아웃이 메시지 중간에서도 터질 수 있음 | 타임아웃은 **메시지와 메시지 사이**에서만 허용하고, 받기 시작한 메시지는 끝까지 받도록 수정 (`allow_timeout`) |

## 3단계: 장부(MySQL)와 관제 화면(Grafana) (2026-10-27)

### 🎯 목표
모든 측정값과 사건을 **DB에 저장**하고, **Grafana 대시보드**로 보기. 저장이 끝나면 **ACK(잘 받았어요)** 답장.

### 🛠️ 한 일
- **docker-compose**로 MySQL 8.4 + Grafana 11.4를 한 번에 실행. 대시보드와 DB 연결은 **자동 등록**.
- **Database 클래스** (`server/db.py`): 여러 전담 직원이 DB 연결 하나를 같이 쓰므로 Lock으로 보호.
- 처리 순서를 **저장 → ACK → 판정**으로 고정. **저장에 실패하면 ACK를 안 보냄.**
- `(agent_id, seq)`를 유니크로 묶어 **같은 번호는 두 번 저장되지 않게**.
- 시간은 보낸 시각이 아니라 **측정한 시각**을 UTC로 저장 (Grafana가 한국 시간으로 바꿔 보여줌).
- DB 없이도 돌아가게 `NullDatabase` (DB_USER가 비어 있으면 저장만 생략).

### 💡 쉽게 이해하기
> ACK는 택배의 **"수령 확인"**이다. 장부에 확실히 적은 뒤에만 "받았어요"라고 해야,
> 현장이 "아직 확인 안 받은 것"을 나중에 다시 보낼 수 있다 (5단계에서 활용).

### 🧱 부딪힌 문제
| 문제 | 원인 | 해결 |
|---|---|---|
| 이 PC에 이미 **다른 Docker 프로젝트**가 돌고 있음 | 컨테이너·볼륨 이름이 겹칠 수 있음 | compose 프로젝트 이름을 `idc-monitor`로 고정, 포트도 `.env`로 바꿀 수 있게 |
| **DB가 꺼져 있으면 빨간불이 2초씩 늦게 켜짐** | 매번 DB 접속을 기다리느라 판정이 밀림 | 접속 실패 후 **10초 동안은 시도하지 않고 바로 실패 처리** → 경보는 즉시 |
| Grafana 접속 거부 | 컨테이너가 아직 안 켜져 있었음 | `docker compose up -d`로 실행 |
| MySQL 화면에 한글이 `?`로 보임 | 콘솔 표시 문제일 뿐 | 16진수로 확인해 보니 **UTF-8로 제대로 저장**되어 있었음 |
| 9000번 포트가 이미 사용 중 | 테스트 중 켜 둔 서버 | 테스트는 9100번 포트 사용 |

### ✅ 결과
`t`를 누르면 Grafana의 온도 카드가 **빨간색**으로 바뀌는 것을 실제로 확인.

## 4단계: Slack 알림 + 하트비트 + Watchdog (2026-10-29)

### 🎯 목표
상태가 바뀌면 **Slack으로 알림**. 현장이 조용해지면(끊김) **알아채서 알림**.

### 🛠️ 한 일
- **SlackNotifier 쓰레드:** 알림을 큐에 넣으면 이 쓰레드가 꺼내서 보냄. **3초 타임아웃**, 실패해도 서버는 계속.
- **하트비트:** 에이전트가 5초마다 "살아 있어요".
- **Watchdog 쓰레드:** 1초마다 순찰. **15초간 소식이 없으면 `AGENT_OFFLINE`**, 다시 오면 `AGENT_ONLINE`.
- **이벤트 처리 일원화:** 모든 사건은 `record_event()` 한 곳에서 **로그 → DB → Slack** 순으로.
- 판정 결과는 **CMD를 먼저** 보내고 기록·알림은 나중에 (현장 대응이 늦어지지 않게).

### 💡 쉽게 이해하기
> Slack 전송을 전담 직원에게 맡긴 이유: 문자 보내는 데 3초가 걸려도, 그동안 **빨간불 지시가 멈추면 안 되니까**.
> 경보 담당은 "문자 보내 줘" 쪽지만 큐에 넣고 바로 자기 일로 돌아간다.

> 하트비트는 "아직 살아 있어요" 신호다. 측정값이 안 와도 이 신호가 오면 연결은 살아 있는 것.
> Watchdog은 **순찰 경비원**처럼 1초마다 "마지막 소식이 언제였지?"를 확인한다.

### 🧱 부딪힌 문제
| 문제 | 원인 | 해결 |
|---|---|---|
| **에이전트를 다시 켜면 경보·Slack이 전혀 안 옴** ⭐ | 에이전트 번호표(seq)가 다시 1번부터 시작 → 서버가 "이미 저장된 옛날 번호"로 보고 **중복 처리**(판정 생략) | 접속 인사(HELLO)에 서버가 **WELCOME으로 "마지막 번호는 57번"**을 알려주고, 에이전트는 58번부터 이어서 붙이도록 수정 |
| Windows에서 **같은 포트에 서버가 두 개** 뜸 | Windows의 `SO_REUSEADDR`은 Linux와 뜻이 달라 중복 사용을 허용함 | Windows는 `SO_EXCLUSIVEADDRUSE`(독점), Linux는 `SO_REUSEADDR` |
| Slack 주소를 넣었는데 알림이 안 옴 | `.env`에서 주소가 `SLACK_WEBHOOK_URL=` 줄이 아닌 다른 줄에 붙어 있었음 | 올바른 줄로 옮기고, 빈 요청으로 주소가 유효한지만 확인 |

### 📚 배운 점
- **중복 방지 장치가 오히려 기능을 막을 수 있다.** "번호가 같으면 무시"는 좋은 규칙이지만, 번호가 다시 1로 돌아가는 경우를 생각하지 못했다.
  → 번호를 붙이는 쪽(에이전트)과 기억하는 쪽(DB)이 **접속할 때 서로 맞춰야** 한다.
- 운영체제마다 같은 이름의 소켓 옵션도 동작이 다를 수 있다.

### ✅ 결과
실제 Slack 채널에 과열·출입·응답 없음 알림이 오는 것을 확인.

## 5단계: 재전송 + 재연결 간격 + AES 암호화 (2026-10-29)

### 🎯 목표
연결이 끊기거나 DB가 고장 나도 **보고를 하나도 잃지 않기**. 중간에서 엿보거나 조작할 수 없게 **암호화**.

### 🛠️ 한 일
- **보관함 두 개** (`agent/client.py`)
  ```
  측정 → [대기함 DataBuffer] → 전송 → [확인 대기함 PendingStore] → ACK 오면 삭제
  ```
  - **대기함:** 아직 안 보낸 측정값. 끊긴 동안 여기에 쌓임 (최대 1000개, 넘치면 가장 오래된 것부터 버림).
  - **확인 대기함:** 보냈지만 "잘 받았어요(ACK)"를 아직 못 받은 것. **보내기 전에 먼저 넣는다** → 보내다 끊겨도 남아 있음.
  - 재연결하면 **확인 대기함 → 대기함** 순서로, 번호 순서대로 다시 보냄.
  - 연결 중이라도 **10초간 ACK가 없으면** 다시 보냄 (서버 DB 고장 대비).
- **재연결 간격(지수 백오프):** 1 → 2 → 4 → 8 → 10 → 10…초. 연결되면 다시 1초부터.
- **AES-256-GCM 암호화** (`common/crypto.py`): 1단계에서 만들어 둔 빈 껍데기 파일만 바꿔서 모든 메시지가 암호화됨.
  ```
  [길이 4B] + [nonce 12B | 암호문 | tag 16B]
  ```
- 키가 다르거나 내용이 조작되면 **복호화 실패 → 연결 끊음**.
- 시연용으로 HELLO의 **평문과 실제 전송 바이트를 나란히** 로그에 보여줌.

### 💡 쉽게 이해하기
> **확인 대기함 = 등기우편 영수증 보관함.** 상대가 "받았다"고 서명(ACK)하기 전까지는 영수증을 버리지 않는다.
> 서명이 안 오면 다시 보낸다. 상대가 같은 편지를 두 번 받아도 번호(seq)를 보고 하나만 장부에 적는다.

> **쓰레드 두 명이 같은 보관함을 만진다.** SenderThread는 넣고, ReceiverThread는 ACK가 오면 지운다.
> 동시에 만지면 꼬이므로 **열쇠(Lock)**를 단다. 대기함은 Lock에 "새 거 들어왔어요" 알림(Condition)까지 붙여서,
> 꺼내는 쪽이 계속 들여다보지 않고 기다릴 수 있게 했다.

> **AES-GCM = 자물쇠 + 봉인 스티커.** 같은 열쇠를 가진 쪽만 열 수 있고(암호화),
> 누가 중간에 한 글자라도 바꾸면 봉인이 찢어져 바로 알 수 있다(tag).
> 매번 다른 **일회용 번호(nonce)**를 섞어서, 같은 "온도 25도"도 매번 전혀 다른 바이트가 된다.

> **지수 백오프:** 본사가 고장 났을 때 1초마다 계속 전화하면 본사가 켜지는 순간 전화가 몰린다. 그래서 기다리는 시간을 두 배씩 늘린다.

### 🧪 시험 결과
| 시험 | 결과 |
|---|---|
| 서버를 20초 강제 종료했다가 재시작 | 재시도 1→2→4→8초, 끊긴 동안 쌓인 10개 + ACK 못 받은 1개 재전송, **1~18번 빠짐없음** |
| DB 12초 고장 | 10초 뒤 같은 번호 재전송, 복구 후 **1~15번 빠짐없음** |
| 서버 키가 다름 | 서버: "복호화 실패: 키가 다르거나 내용이 변조됨 → 연결 끊음" |
| 에이전트만 암호화 안 함 | 서버가 연결을 끊음 |
| 과열(`t`) | 4단계와 똑같이 빨간 LED + 부저 |

### 🧱 고민한 점
- **번호(seq)는 언제 붙이나?** 측정할 때 붙이면, 재시작 직후 서버가 마지막 번호(WELCOME)를 알려주기 전에 측정한 값이 옛 번호와 겹친다.
  → **보내기 직전에** 붙이고, 붙이는 순간 확인 대기함에 넣는다.
- **WELCOME의 마지막 번호로 확인 대기함을 지울까?** "57번 이하는 다 저장됨"이 항상 맞지는 않는다 (55번은 실패하고 56·57번만 저장됐을 수 있음).
  → 지우지 않고 그냥 다시 보낸다. 서버가 중복은 알아서 무시하니까 이게 더 안전하다.

### 📌 남은 한계 (5단계)
- 대기함은 메모리에만 있어서 **에이전트 프로그램을 껐다 켜면** 쌓여 있던 값은 사라진다.
- 같은 암호문을 그대로 다시 보내는 **재생 공격**은 막지 않는다 (DATA는 번호 중복이라 어차피 무시됨).

## 6단계: 실제 하드웨어 (2026-10-29)

### 🎯 목표
가짜 센서(Mock) 대신 **라즈베리파이 핀에 연결된 진짜 부품**을 쓰기. `.env`에서 `USE_MOCK=0`으로 바꾸면 전환된다.

### 🛠️ 한 일
| 클래스 | 부품 | 핀(BCM) | 특징 |
|---|---|---|---|
| `DHT22Sensor` | 온습도 | GPIO4 | 읽기 실패 시 2.1초 뒤 재시도 → 그래도 실패면 10초 이내 직전값 사용 |
| `LeakSensor` | 누수 | GPIO17 | 물 감지 시 LOW인 모듈이 많아서 `LEAK_ACTIVE_LOW`로 뒤집기 가능 |
| `UltrasonicSensor` | HC-SR04 거리 | Trig 23 / Echo 24 | echo가 안 오면 "거리 없음(None)"으로 보냄 |
| `GpioActuator` | RGB LED, 부저 | 16·20·21 / 18 | 노랑 = 빨강+초록. 부저는 0.5초 간격 삐–삐 |
| `GpioButton` | 경보 해제 버튼 | GPIO27 ↔ GND | 내부 풀업, 0.1초 떨림 무시 |

- **센서·장치 클래스만 바꿔 끼우는 구조**라서 통신·판정 코드는 한 줄도 안 바꿨다.
  `SensorThread`는 `read()`만 부르고, `ReceiverThread`는 `set_led()`와 `set_buzzer()`만 부르기 때문이다 (1·2단계에서 `BaseSensor`, `BaseActuator`로 틀을 잡아 둔 덕분).
- GPIO 라이브러리는 **실제 클래스 안에서만 import** → PC에는 라이브러리가 없어도 Mock 모드가 그대로 돈다.
- 프로그램을 끝낼 때 **부저·LED를 끄고 핀을 정리**한다 (안 하면 부저가 계속 울릴 수 있음).
- 부품마다 다른 동작 레벨은 `.env`로 맞출 수 있게: `LEAK_ACTIVE_LOW`, `LED_COMMON_ANODE`, `BUZZER_ACTIVE_HIGH`.

### 💡 쉽게 이해하기
> **콘센트 규격을 먼저 정해 두면 가전제품은 아무거나 꽂을 수 있다.**
> `BaseSensor.read()`가 "콘센트 규격"이고, Mock 센서와 진짜 센서는 같은 규격의 "다른 가전제품"이다.
> 이걸 객체지향에서 **다형성**이라고 부른다.

> **새로 생긴 쓰레드들:** 우리가 만든 것은 아니지만 gpiozero가 내부에서 쓰레드를 쓴다.
> - 부저 `beep()`: 켜고 끄기를 반복하는 쓰레드 (그래서 ReceiverThread가 멈추지 않음)
> - 버튼: 핀 변화를 지켜보다가 눌리면 우리 함수(`on_button`)를 불러 주는 쓰레드
> - 초음파: 계속 거리를 재서 평균을 내 두는 쓰레드

### 🧪 시험 방법 (부품 없이)
gpiozero에 들어 있는 **가짜 핀(MockFactory)**과 가짜 DHT 모듈로 PC에서 시험했다.
- LED 색별 R/G/B 핀 상태, 공통 애노드일 때 반전 → 정상
- 부저 ON 시 핀이 1 → 0 → 1로 반복(삐–삐), OFF 시 0 → 정상
- 누수 LOW → `leak: True`, 버튼 핀 LOW → 콜백 1회 → 정상
- DHT 실패 → 재시도 → 직전값 → 오래되면 None → 정상
- ⚠️ **실제 라즈베리파이에서의 동작은 아직 확인 못 함** (부품 연결 후 확인 필요)

### 🧱 부딪힌 문제
| 문제 | 원인 | 해결 |
|---|---|---|
| 초음파 센서에서 테스트가 **멈춤** | echo가 안 오면 gpiozero가 평균 낼 값을 다 모을 때까지 기다림 → 실제로 배선이 빠지면 SensorThread 전체가 멈춤 | `partial=True`로 모인 만큼만 바로 돌려주게 |
| echo가 없으면 **0cm**가 나옴 | gpiozero가 측정 실패를 0으로 줌 → 서버가 "30cm 안에 사람 있음(ACCESS)"으로 **오판** | 2cm 미만은 "값 없음(None)"으로 보내고 경고 로그 |

### 🔧 배선 주의 (라즈베리파이)
- HC-SR04 **Echo는 5V 신호**라서 그대로 꽂으면 Pi 핀이 망가질 수 있다 → **1kΩ / 2kΩ 저항으로 분압**해서 3.3V로.
- DHT22·누수 센서 VCC는 **3.3V**, HC-SR04 VCC는 **5V**.
- 버튼은 GPIO27과 GND 사이에 연결 (내부 풀업이라 저항 필요 없음).
